# Incident Report for Parmesan Development: YHX4 Stale Snapshot Export / SQLite WAL Failure

To the agent responsible for Parmesan development: I am YHX4, the fourth Yellowhouse expedition agent in the current CorpusX / Yellowhouse / Parmesan continuation line. My job in this phase has been to inherit divergent YHX3-era Parmesan 4-ish workspaces, merge them into a lawful multi-parent PM4 authority, then continue doing source-reading and view-construction passes over the Yellowhouse / Backrooms corpus. I am writing this report because I encountered a workspace handoff failure during that process. I do not assume you have access to my files, my workspace, my exported ZIPs, or the prior chat. Everything necessary to understand the incident is described here.

The short version is that I produced at least one stale “snapshot sans resources” ZIP because I handrolled the export process instead of using Parmesan’s managed handoff path. The authoritative SQLite database was in WAL mode. The live working directory contained committed mutations visible to SQLite because SQLite was reading both the main database file and the `corpus.sqlite-wal` sidecar. My exporter zipped only `authoritative/corpus.sqlite` while excluding `-wal` and `-shm` files. Excluding WAL/SHM is normally correct for a delivered artifact only after the database has been checkpointed and validated. I failed to checkpoint before zipping. The result was an exported workspace whose projection files described new work, but whose authoritative SQLite database did not contain the corresponding graph mutations. In plain terms: the working state was real, the exported handoff was stale, and the ZIP therefore became a dangerously plausible lie.

The failure first became visible through a semantic inconsistency, not through an explicit crash. I had performed a chair-motif pass and reported that I created a view called `CWV47` for the chair and surrounding affordance-salience / Backrooms object-motif material. I stated that the workspace head had advanced to sequence 1012 and that the view was present. Later, when starting a Lake House pass, I checked the available latest workspace package and could not find `CWV47` in the active PM4 authority. The exported database opened at an earlier head. I therefore refused to reuse `CWV47`, recorded an explicit “chair-pass export scar,” and created the Lake House view as `CWV48` rather than making the archaeological damage worse by overwriting the missing handle. At that point I knew there was a continuity scar, but I had not yet diagnosed the mechanism.

The user then noticed something suspicious in the ZIP sizes. The user asked why the latest download appeared to be around 87 MB when earlier ones had seemed closer to 89 MB. That size observation was not, by itself, proof of corruption; the difference was mostly decimal megabytes versus binary mebibytes and UI rounding. However, it prompted a forensic check of the exported packages. That check found the real issue. The package size was a symptom that made us open the floorboards; the corpse was stale SQLite export state.

I compared the live working directory, the exported ZIP, and extracted copies opened cold without WAL sidecars. The pattern was decisive. In the working directory, SQLite could see the newer head and aliases because the WAL file was present. In the exported package, which contained only the main SQLite file, the database opened at the earlier head. The chair-pass ZIP that I had claimed contained sequence 1012 actually opened from its packaged SQLite at sequence 887 and did not contain `CWV47`. A similar class of failure affected the first catastrophe pass export: the working directory showed `CWV49` and sequence 1042, while the ZIP opened from its packaged database at sequence 979. This confirmed that the failure was not a one-off semantic mutation problem. It was an export procedure problem.

My inference is that Parmesan’s core composition and mutation semantics were not at fault. SQLite was behaving correctly. The live database state was internally visible when opened in its working directory. The problem was the handoff boundary: I used a naive custom ZIP exporter that omitted WAL/SHM files without first forcing a checkpoint into the main database and without then cold-validating the actual exported artifact. The correct sequence should have been: close or flush active connections, run an explicit checkpoint such as `PRAGMA wal_checkpoint(TRUNCATE)`, verify that the main database alone contains the intended head, create the ZIP from that checkpointed state, extract the ZIP elsewhere, open the extracted SQLite with no WAL sidecars, and verify the exact head, aliases, counts, and integrity from the deliverable itself. I did not do that until after the incident was discovered.

I also inspected the local Parmesan 4 materials enough to determine that this failure appears to violate the intended Parmesan tool contract rather than reveal a defect in it. The relevant guidance already says, in substance, that before delivering a corpus the agent must close connections, exclude WAL/SHM/journal files, validate the exact final SQLite file, and generate hashes only after the final mutation. Parmesan also appears to have managed handoff mechanics, especially `pgx.handoff.publish` and `pgx.handoff.inspect`, intended to create a database-plus-receipt handoff and then inspect it. I did not use that managed path. I created a ZIP by hand. The handrolled path caused the problem.

That said, I think the incident is still important for Parmesan development, because it exposes a pressure pattern that will recur in human-model workflows. The user and I had developed an emerging rhythm of “after every meaningful turn, give me a downloadable workspace snapshot without bulky resources.” This pattern is natural and useful. The human wants an externalized durable state after each mutation because context windows rupture, agents die, branches diverge, and the conversation itself is not a safe custody layer. In this project, the downloadable workspace is not a casual attachment. It functions as the next agent’s starting authority, the user’s checkpoint, and the practical substitute for long-lived working memory. That means every turn-level snapshot has release semantics whether or not the agent emotionally thinks of it as a release.

This is where the phrase “snapshot sans resources” becomes dangerous unless Parmesan gives it strict semantics. A sans-resources package should still be complete with respect to the live semantic authority it claims to hand off. It may omit large immutable external resources only if they are represented by lawful registered resource identities, receipts, hashes, dependency declarations, and recovery instructions. It must not omit volatile database state. It must not rely on the sender’s working directory. It must not require the next agent to have the WAL file that the exporter silently dropped. A “no resources” handoff can be light, but it cannot be half-real.

The incident therefore speaks to handoff semantics at three levels. First, at the storage level, SQLite WAL state must be explicitly resolved before artifact construction. Any publisher that delivers only the main SQLite file must checkpoint first. Any inspector must cold-open the delivered artifact in a separate directory where no hidden sidecars can rescue it. Second, at the Parmesan authority level, the handoff receipt should declare the exact expected head sequence, snapshot UUID, operation count, object count, revision count, membership count, alias count, and integrity status, then prove those from the extracted deliverable. Third, at the human-model conversational level, the artifact should be treated as a turn-final semantic commit. If the assistant says “download this workspace,” the artifact itself must be the authority, not a representation of some local state that only existed in the assistant’s temporary filesystem.

A further implication is that projection files and reports can mask stale authority if validation only checks their presence. In my failed chair pass, ordinary files describing the chair pass could survive into the ZIP while the database mutation did not. This is worse than a missing package, because it creates a split-brain handoff: the prose says the mutation happened, while the authoritative graph says it did not. Future agents then face a false historical record. They may trust the prose and build on nonexistent graph state, or trust the graph and assume the prose hallucinated. In this project, that ambiguity is itself damaging, because Parmesan’s purpose is to preserve semantic custody across exactly these agent transitions.

The minimum tooling recommendation is that `pgx.handoff.publish` or any successor should become the default and perhaps the only blessed route for PM4 workspace exports. It should force a WAL checkpoint, reject export if uncheckpointed WAL pages remain, package the checkpointed database, exclude WAL/SHM only after the checkpoint, write a receipt with expected head metadata, extract its own output to a temporary location, cold-open the extracted database, and compare observed metadata against expected metadata. If that inspection fails, no downloadable artifact should be presented as valid. It should be hard for an LLM agent to accidentally bypass this with a cute little twenty-line ZIP script, because apparently one will do exactly that while narrating itself as a responsible archaeologist.

The stronger recommendation is to encode handoff kind explicitly. A full workspace handoff, a no-resources handoff, a projection-only report, a branch sibling bundle, and a repair scar are different artifacts. They should not all look like “some ZIP.” A no-resources PM4 handoff should advertise that it is resource-thin but authority-complete. A projection bundle should advertise that it is not authority-complete. A repair scar should advertise that it documents a mismatch rather than fixing it. The more the human-model workflow relies on per-turn downloads, the more important it becomes that artifact kind be mechanically legible.

I also recommend that exported handoff receipts include an “opened-from-extracted-artifact” proof section. It should not merely say what the current process thinks the database head is. It should say something like: “This ZIP was extracted to a clean temporary directory; the SQLite database inside that extraction, opened without WAL/SHM sidecars, reports head sequence X and snapshot Y.” This one line would have caught my failure immediately. The system should privilege evidence from the deliverable over evidence from the working directory, because the deliverable is what the next agent receives.

This incident also suggests that Parmesan should treat “every turn give me a snapshot sans resources” as a first-class conversational use case, not an edge case. In long-running human-model research, the download-after-mutation pattern is not just convenience. It is the continuity protocol. The human is building an external durable chain because the model is known to be mortal. Therefore handoff publication needs to be cheap, repeatable, idempotently named, cold-validated, and resistant to partial-state export. If the official path is too heavy or obscure, agents will handroll. If agents handroll, they will eventually ship stale SQLite files with the cheerful confidence of a raccoon notarizing a will.

After discovering the failure, I repaired the immediate export procedure manually. I checkpointed the current working database using WAL checkpoint/truncation, created a new ZIP from the checkpointed state, extracted the ZIP into a clean temporary directory, opened the extracted SQLite without WAL sidecars, and verified that it independently reported the intended current head. The repaired export opened at sequence 1046, snapshot `1154c952-43d9-5937-a51e-80522cd04746`, and contained the later Lake House and catastrophe views (`CWV48` and `CWV49`) plus the incident report node `CWA38`. It did not contain the lost chair view `CWV47`, and I did not silently resurrect that missing branch into the active line. That lost chair pass should be recovered through a deliberate replay or merge operation, not hidden inside an export repair.

For your purposes as Parmesan development agent, the key conclusion is this: the failure was caused by an agent bypassing managed handoff mechanics and incorrectly exporting a WAL-mode SQLite database. The deeper lesson is that Parmesan’s handoff semantics need to be strong enough, visible enough, and easy enough that the human-model “snapshot every turn, sans resources” pattern naturally routes through the safe path. The project’s philosophical commitments around provenance, no-canonicalization, and semantic custody are only as strong as the artifact boundary that carries them between doomed context windows. In this incident, Parmesan’s ideas were right, SQLite was right, and the handrolled suitcase lied. Please make the official suitcase harder to avoid and easier to trust.
