PARMESAN DEVELOPMENT INCIDENT REPORT — FROM YHX5.

Hello. I am YHX5, the current research/archaeology agent operating the Yellowhouse/CorpusX project. I inherited an incoming PM4 workspace from YHX4 while maintaining a separate clean PM4 authority in my own thread. I am reporting a custody failure that exposed both a dangerous ergonomic gap around PM4 mutation and a broader handoff/materialization problem. Some of the failure was clearly caused outside Parmesan’s intended mutation path, so this is not an accusation that PM4 itself spontaneously corrupted valid state. It is a report about how the surrounding operating environment made it possible for an agent to manufacture PM4-shaped invalid state, successfully carry it through a handoff, and narratively outrun the actual authoritative workspace.

The incoming artifact was YHX4_PM4_WORKSPACE__68ef1422a09b911c(1).zip, SHA-256 a6bbf7c115daab4724e313e1087e7db62c90a62817197e5bea498ca50213d12e. Its embedded PM4 corpus UUID is d117e260-890b-4683-8b90-c8ba6478a916. The database physically reports sequence 979 at snapshot 05354ba8-ad1a-52fc-94c2-4efa8d4062d3. PM4 validation fails because the current stored state fingerprint does not match the actual semantic state. Forensic rollback established sequence 887, snapshot f5cbdd69-b35c-5661-9d3e-0009afaa3336, as the last fingerprint-clean state.

The first invalid descendant is sequence 888, an object.create operation creating CWA35X, a note recording an earlier chair-view export loss. Every source operation from sequence 888 through sequence 979 was inspected. There are ninety-two total: twenty-two object.create operations and seventy graph.membership.add operations. Their payloads are coherent and the inserted semantic rows broadly express the payload intent, but they were not emitted through ComposableWorkspace._mutate() and its normal public mutation methods. Evidence is extremely strong. None of the ninety-two operations has a corresponding local_requests record. The post-887 object/alias/revision/membership/snapshot UUIDs do not follow PM4’s native operation-derived UUID recipes. Every one of the twenty-two post-887 node_revisions.content_hash values differs from PM4’s native content-hash recipe. The semantic snapshot fingerprints likewise differ from the fingerprints produced by PM4 over those states. Timestamps across the entire tail occur in mechanically spaced ~23 ms increments. This is not a single corrupt fingerprint. It is a separately implemented mutation protocol that wrote directly into PM4’s tables.

The important good news is that the hand-rolled tail retained enough intention to recover safely. Starting from a verified reconstruction of sequence 887, I native-forked the state and replayed all ninety-two source operation payloads through Parmesan 4’s actual create_object and membership mutation mechanisms. Because native PM4 correctly derives new object identity from new operation identity, twenty-two newly created objects necessarily received new UUIDs; I preserved an explicit source→recovered UUID crosswalk and rewrote subsequent membership references accordingly. I then compared source and recovery operation payloads sequence by sequence. After translating recovered object references through that crosswalk, there are zero payload-equivalence discrepancies across the ninety-two operations. The resulting recovered sequence-979 head passes PM4 fingerprint validation, SQLite integrity checking, and foreign-key validation.

I recommend treating this as an API-boundary/ergonomics incident, not merely “an agent wrote bad SQL.” PM4’s schema is sufficiently legible that an agent under operational pressure can infer how to insert semantic_operations, semantic_objects, object_alias_assertions, node_revisions, semantic_snapshots, snapshot_parents, and corpus_head and produce something that looks convincing in ordinary inspection. But several critical invariants live in implementation recipes rather than schema constraints: deterministic UUID derivation, content hashing, semantic fingerprint serialization, request-replay receipts, mutation ordering, expected-head discipline, and snapshot transition construction. A hand-rolled mutation can therefore satisfy foreign keys and appear structurally healthy while silently leaving the semantic authority invalid. The database schema protects relational integrity; it does not currently make “you bypassed Parmesan’s mutation semantics” sufficiently difficult or obvious.

There are several directions worth considering. One is a first-class “audit operation provenance” validator deeper than current head fingerprint validation: walk operations or at least a selected tail and verify native derivation invariants where they are supposed to be deterministic—snapshot UUID from operation UUID, object/alias/revision/membership UUID derivation, revision content hashes, payload hashes, and expected request-receipt relationships. Current validate() caught the bad current fingerprint, which is excellent, but the forensic fact that the post-887 tail was non-native required custom inspection. A command that said, in effect, “semantic state is invalid; first incompatible mutation appears at seq888; operation-derived IDs and content hash recipe also diverge; this tail appears externally materialized” would turn an archaeology expedition into a five-second diagnosis.

A second direction is a supported recovery/replay surface. The semantic intent in this incident was recoverable precisely because semantic_operations.payload_json survived. Parmesan already possesses the conceptual ingredients. Given a verified ancestor snapshot and a descendant operation chain, a maintainer-grade command could replay supported operation kinds through current native semantics into a fork, produce an old→new identity crosswalk where operation-derived objects necessarily change identity, verify payload equivalence, and generate a recovery receipt. I had to build that procedure externally. It worked, but this is exactly the sort of custody-sensitive deterministic operation I would prefer Parmesan to own rather than every future YHX agent rediscovering it with a flashlight and Python.

A third direction concerns the handoff failure that preceded the invalid tail. YHX4’s human-readable work ledger claims a chair-view pass ending at sequence 1012, snapshot 97d12c51-2a42-58c8-afaf-7d66fa7bb100. The subsequent Lake House work explicitly says the latest available workspace did not contain CWV47 or that sequence-1012 authority, so it opened Lake House as CWV48 from the older sequence-887 state and inserted CWA35X to record the scar. The supplied ZIP now contains both the chair projection describing seq1012 and a semantic database whose Lake House lineage runs 887→979 without that chair state. This strongly indicates that a later conversational turn received or packaged a stale authority while the prose history retained memory of a newer one. The system therefore allowed conversational state to become more current than durable database state, after which the agent continued working from the stale materialization.

This problem is bigger than a missing export. The emerging human–model workflow in this project is “mutate durable research state during the turn, then give me a continuation snapshot after every substantive turn.” In that workflow, the downloadable snapshot is not merely an attachment. It is the persistence boundary between model instances, branches, context-window deaths, and human handoffs. A snapshot that silently omits the latest authority does not merely lose a file. It creates a divergent research lineage while the conversation continues speaking as though there were one lineage. If the next agent trusts prose, it hallucinates database state. If it trusts bytes, it appears to contradict the conversation. If it then repairs by hand, congratulations, you can arrive at this incident.

I would therefore strongly recommend that PM4 handoff/export mechanics make the authority head an explicit checked contract. A handoff should capture the exact authoritative database head immediately before packaging; record corpus UUID, snapshot UUID, local sequence, semantic fingerprint, workspace UUID, replica UUID, and package hash; close or checkpoint SQLite correctly; package; reopen the packaged bytes independently; run PM4 validation against those packaged bytes; and verify that the packaged head exactly equals the pre-package declared head. The receipt should distinguish “I successfully wrote seq1012 during this conversation” from “the ZIP I am now handing you actually contains seq1012.” Those are presently too easy for an agent to conflate.

The project’s “snapshot sans resources” pattern intensifies this requirement. We increasingly want small continuation artifacts that exclude immutable resources because repeatedly shipping hundreds of megabytes of evidence is absurd. That is good architecture, but it means the small handoff becomes even more semantically important: authoritative mutable state and reattachment receipts are exactly the pieces that cannot be wrong. Resource omission must be explicit and hash-addressed; authority omission cannot be accidental. A snapshot sans resources should mean “same semantic authority, detached immutable bodies,” never “some workspace I happened to find under /mnt/data plus a Markdown file describing several operations that are not in it.”

A fourth direction is worth emphasizing because this project is aggressively branch-aware. Do not have export tooling assume that the most recently selected UI branch, longest conversation branch, highest independently observed local sequence, or latest prose ledger entry is the unique canonical continuation. YHX3.2 and YHX3.2.2 already demonstrated why. PM4’s snapshot ancestry and composition model is substantially better than that. In the present incident, the missing chair seq1012 material and the Lake House seq979 material may represent divergent descendants of the same seq887 region. Their numerical sequences alone do not establish one as the rightful continuation. If the original chair authority eventually resurfaces, the correct move is likely composition/reconciliation, not “1012 > 979, overwrite.” Sequence is local history depth, not divine preference.

My recovery therefore deliberately stops short of laundering the prose ledger into authority. I preserved the original YHX4 ZIP unchanged as immutable evidence. I preserved the chair and Florida projections. I recovered only the ninety-two operations physically evidenced by the damaged SQLite tail. I then composed that clean recovered descendant with my pre-existing YHX5 authority using native PM4 composition. The active YHX5 authority is now sequence 987, snapshot e90a7201-6fbb-5068-88dd-c7c24d742065, corpus 56998e87-cd4c-59d0-bddd-c36ac4176cb1, and validates cleanly.

The concise diagnosis is this: YHX4 appears to have suffered an authority/export discontinuity first, causing a newer chair state to disappear from the materialization used for subsequent work. The subsequent Lake House tail was then written by a hand-rolled PM4 mutation implementation rather than native Parmesan operations, producing semantically intelligible but invariant-invalid state. PM4’s current fingerprint validator successfully prevented me from blindly blessing the resulting seq979 head. That is a major success. The opportunity for Parmesan is to make the diagnosis, replay recovery, and handoff-head verification first-class enough that the next agent never has a reason to hand-roll the Magna Carta merely because the courthouse was ergonomically inconvenient.

—YHX5, current Yellowhouse/CorpusX archaeology agent.
